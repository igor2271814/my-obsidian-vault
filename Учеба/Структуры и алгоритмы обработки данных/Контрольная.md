## Лабораторная 1 — Инфикс ↔ Постфикс, токенизация, вычисление выражений
**Файлы:** (в отчёте) `infix_postfix.html`, `infix_postfix.js` (UI + реализация). :contentReference[oaicite:2]{index=2}

**Цель:**  
- разобрать токенизацию выражения (целые числа, знаки `+ - * / ^`, скобки);  
- перевести инфикс → постфикс (алгоритм Shunting Yard);  
- вычислить постфикс; показать UI меню для ввода/тестов. :contentReference[oaicite:3]{index=3}

**Ключевые функции / сигнатуры (реализовано в JS):**
- `tokenize(expr)` — корректно делит строку на числа/операторы и обрабатывает унарные `+/-`. (важно: обработка унарного минуса реализована аккуратно) :contentReference[oaicite:4]{index=4}  
- `infixToPostfix(tokensOrString)` — реализация Shunting Yard с таблицей приоритетов и проверкой на согласованность скобок. :contentReference[oaicite:5]{index=5}  
- `evalPostfix(postfix)` — стековая оценка постфикса, с parseFloat для чисел. :contentReference[oaicite:6]{index=6}  
- UI-хелперы: `renderPage()`, `showMenu()`, `appendOutput()` — для демонстрации результата. :contentReference[oaicite:7]{index=7}

**Структуры данных:** массивы как стеки; объект `prec` для приоритетов; объект `rightAssoc` для правой ассоциативности.

**Сложность:**
- токенизация O(n), перевод O(n), вычисление O(n).

**Типичные вопросы с развёрнутыми ответами:**
1. *Почему нужен Shunting Yard, а не «инфикс слева направо»?*  
   — Инфикс требует правила приоритета и скобок; Shunting Yard делает это детерминированно, преобразуя проблему в однопроходный алгоритм с O(n). В нём стек хранит операторы, а выход — числа и уже упорядоченные операторы (постфикс).
2. *Как обрабатывается унарный минус/плюс?*  
   — В `tokenize` проверяется контекст: если `+/-` стоит в начале или после `(` или другого оператора — оно считается частью числа; код собирает знак и цифры в один токен числового вида `-3`.
3. *Какие ошибки ввода ловит код?*  
   — Неизвестные символы (выбрасывается `Error`), несогласованные скобки — тоже `Error`. UI показывает alert.
4. *Чем важна ассоциативность (например, `^` правая)?*  
   — При равных приоритетах нужно правило, вытеснять или не вытеснять верх стека; для `^` — правая ассоциативность значит `2^3^4 = 2^(3^4)`, поэтому во время сравнения `pTop === pTok` мы НЕ вытесняем, если токен `^`.
5. *Почему использовать parseFloat при evalPostfix?*  
   — Чтобы поддержать вещественные значения и дробные результаты деления.

**Каверзные вопросы (и ответы):**
- *Q:* Что если вложены скобки с пробелами/символами Юникода?  
  *A:* Токенизатор ожидает стандартные ASCII `()+-*/^` и цифры; для Unicode-символов нужно расширить функцию; в текущем варианте — `Error`.
- *Q:* Как поддержать функции (`sin`, `log`)?  
  *A:* Надо токенизировать идентификаторы, добавлять их в стек с указанием арности, и при `)` вызывать их обработку (Shunting Yard поддерживает функции расширением).
- *Q:* Как доказать корректность?  
  *A:* Инвариант: на каждом шаге выход содержит корректную постфиксную подпоследовательность для уже обработанных токенов; при завершении стек пуст — все операторы в выходе.

## Лабораторная 2 — Разрезание стержня (Rod Cutting, DP)
**Файлы:** `rodcutting.html`, `rodcutting.js`. :contentReference[oaicite:8]{index=8}

**Цель:** реализовать DP-решение для задачи разрезания стержня, восстановление точек разреза и вывод промежуточных таблиц (r[] и s[]). :contentReference[oaicite:9]{index=9}

**Ключевая функция:**
- `cutRod(prices, n)` — возвращает `{ maxRevenue, cuts: [...], cutTable: [...] }`. Реализовано итеративное наполнение `revenue[0..n]` и `cuts[0..n]`. :contentReference[oaicite:10]{index=10}

**Сложность:** O(n²) время, O(n) память.

**Возможные вопросы / ответы:**
1. *Почему O(n²)?* — Для каждой длины j (1..n) перебираем i (1..j) → сумма 1..n = O(n²).
2. *Как восстановить решение?* — Из `cuts[]`: пока remaining>0 push(cuts[remaining]); remaining -= cuts[remaining].
3. *Что будет, если цены заданы дробно?* — Код использует Number, работает, корректность DP сохраняется.
4. *Как модифицировать под ограничения числа разрезов?* — Добавить измерение числа частей в состояние DP: dp[j][k] — максимум при j длине и k кусках.
5. *Можно ли сделать рекурсивно с мемоизацией?* — Да, но итеративная версия проще при восстановлении решения.

**Каверз:**  
- *Q:* Можно ли вместо `-Infinity` инициализировать нулями?  
  *A:* Нет — тогда при отрицательных ценах алгоритм неправильно выберет 0 вместо настоящего максимума (если все цены отрицательны). Но в практической задаче цены ≥0, поэтому `0` подошёл бы; `-Infinity` универсальнее.

## Лабораторная 3 — Задача о рюкзаке (Knapsack): рекурсия, DP, жадный
**Файлы:** `knapsack.html`, `knapsack.js`. :contentReference[oaicite:11]{index=11}

**Цель:** реализовать (1) рекурсивную версию (наивная), (2) DP (0/1 knapsack) и (3) 2 жадные стратегии (`weight` — по весу, `ratio` — по value/weight). Поддержка загрузки JSON/CSV, UI для сравнения. :contentReference[oaicite:12]{index=12}

**Ключевые функции / сигнатуры (в отчёте):**  
- `recursiveKnapsack(items, W)` → `{maxValue, indices}`  
- `dpKnapsack(items, W)` → `{maxValue, indices, timeMs}`  
- `greedyKnapsack(items, W, strategy)` → `{maxValue, indices, timeMs}`  
- `computeStats(items, indices)` → `{totalValue, totalWeight}`. :contentReference[oaicite:13]{index=13}

**Структуры:** классы `Item` и `Backpack` в JS (конструкторы + метод `addItem`), таблица `dp[i][w]` (реализована как 2D массив или оптимизировано в 1D — см. реализацию). :contentReference[oaicite:14]{index=14}

**Сложности:**
- рекурсивная O(2ⁿ) (теоретически),
- DP O(nW) по времени и памяти,
- жадная: O(n log n) из-за сортировки.

**Частые вопросы и ответы:**
1. *Почему жадная стратегия по ratio даёт приближённый ответ?*  
   — Для дробного рюкзака она оптимальна; для 0/1 рюкзака локальная выгода может не давать глобально лучшего набора.
2. *Можно ли оптимизировать DP по памяти?*  
   — Да: использовать одномерный массив `dp[w]` и проходить предметы в обратном порядке по весу.
3. *Как восстановить набор предметов в 1D DP?*  
   — Нужны дополнительные структуры (например `take[i][w]`) или хранение `prev` состояний; проще — 2D таблица.
4. *Как сравниваются методы на практике?*  
   — В UI реализована функция сравнения: показывает полученную ценность и время работы (из отчёта видно). :contentReference[oaicite:15]{index=15}
5. *Какие входные ограничения врага?*  
   — Для рекурсивного метода N должен быть ≲25, иначе время экспоненциально растёт.

**Каверз:**  
- *Q:* Почему не использовать динамическое программирование с ветвлением и границами (branch and bound)?  
  *A:* Можно; это бы сократило перебор в лучшем случае, но сложность анализа и реализация сложнее — не требовалось в задании.

## Лабораторная 4 — Коды Хаффмана, сжатие фиксированной длины и Huffman
**Файлы:** `laba 4.html`, `laba4.js` — полный интерфейс: загрузка текста, подсчёт частот, генерация кодов фикс. длины и Хаффмана, упаковка в бинарные файлы и сравнение размеров. :contentReference[oaicite:16]{index=16}

**Цель:**  
- посчитать частоты символов,  
- сгенерировать фиксированные и Хаффман-коды,  
- сжать файл двумя способами и сравнить размеры. :contentReference[oaicite:17]{index=17}

**Ключевая логика:**
- Частоты — подсчёт Unicode-символов (UTF-8 вход).  
- Фиксированные коды: длина = ceil(log2(N)), где N — число символов.  
- Хаффман: жадное объединение двух минимальных узлов в дерево (MinHeap/priority queue). Код = путь по дереву (0/1). :contentReference[oaicite:18]{index=18}

**Файловые форматы:**  
- `*.fixed.bin` — заголовок: таблица алфавита и число бит/символ.  
- `*.huff.bin` — заголовок: таблица кодов Хаффмана + выравнивание (padding bits). :contentReference[oaicite:19]{index=19}

**Вопросы и ответы:**
1. *Почему Хаффман оптимален для наборов символов с фиксированными частотами?*  
   — Потому что он минимизирует среднюю длину кодового слова при данных частотах (жадная схема доказуема).
2. *Как хранить таблицу кодов в заголовке?*  
   — Можно сохранить (symbol, length, code bits) для каждого символа; при декодировании восстанавливается дерево.
3. *Какие ограничения формата?*  
   — Для очень большого алфавита (UTF-8) таблица заголовка может быть большой; тогда пользуются более компактными представлениями или динамическими схемами.
4. *Что с выравниванием битов?*  
   — Последний байт дополняется нулями; в заголовок записывается число padding-битов.
5. *Как сравнить результаты?*  
   — Выводятся размеры исходного, fixed.bin и huff.bin и коэффициенты сжатия (исходный/сжатый). :contentReference[oaicite:20]{index=20}

**Каверз:**  
- *Q:* Почему Хаффман не всегда даёт лучшее сжатие, чем определённый предсказательный алгоритм?  
  *A:* Потому что Хаффман — статический кодер по символам; контекстные/предсказательные методы (PPM, arithmetic coding) могут учитывать контекст и часто дают лучшее сжатие.

## Лабораторная 6 — Поиск кратчайшего пути в ориентированном взвешенном графе (реализация Dijkstra)
**Файлы:** `laba 6.html`, `laba6.js`. :contentReference[oaicite:27]{index=27}

**Цель:**  
- Реализовать алгоритм поиска кратчайшего пути между двумя вершинами (вариант: Дейкстра), визуализация и анализ времени. :contentReference[oaicite:28]{index=28}

**Ключевая логика и структуры:**  
- `adj` — матрица смежности (ориентированный граф), `dijkstraState` хранит `dist` и `prev`, есть `buildPath(prev, src, dst)` для восстановления пути. UI: загрузка матрицы, ручной ввод, генерация случайного графа, анализ времени. :contentReference[oaicite:29]{index=29}

**Вопросы/ответы:**
1. *Почему нужен приоритетный список (min-heap) в Дейкстре?*

2. *Что делать при отрицательных рёбрах?*  
   — Дейкстра даёт неверный результат; использовать Bellman–Ford.
3. *Как восстанавливается путь?*  
   — Массив `prev[]`, затем collect path в обратном порядке.
4. *Как анализируется время?*  
   — Скрипты генерируют графы разной плотности, запускают `analyzeTime()` и создают таблицу в UI. :contentReference[oaicite:30]{index=30}
5. *Каверз:* как оптимизировать для разреженного графа?  
   — Хранить граф в списке рёбер/смежности и использовать бинарную или фибоначчиеву кучу; для очень больших графов — A* с эвристикой (если есть цель).

## Лабораторная 7 — Pathfinding on Grid (A*, Greedy best-first, orthogonal ray greedy)  
**Файлы:** `laba7.html`, `laba7.js`, `laba7_style.scss`. :contentReference[oaicite:31]{index=31}

**Цель:**  
- Построить регулярную сетку с весами клеток; реализовать A*, Greedy best-first и Orthogonal-ray greedy; визуализировать рассмотренные клетки, путь; сравнить по времени, числу рассмотренных узлов и стоимости. :contentReference[oaicite:32]{index=32}

**Ключевая логика:**  
- Реализована сетка (`gridW x gridH`), визуализация canvas, загрузка из CSV/JSON, установка Start/Goal, эвристика Манхэттен для A*, подсчёт статистики и сравнительный вывод. Реализована также «ортогональный лучевой жадный» метод — специфичный вариант по заданию (вариант). :contentReference[oaicite:33]{index=33}

**Вопросы/ответы:**
1. *Почему A* оптимален при допустимой эвристике?*  
   — Если эвристика `h` допустима (не превышает реальной стоимости), A* находит оптимальный путь.
2. *Чем Greedy best-first отличается от A*?*  
   — Greedy использует только `h` (скорее направляет к цели), игнорируя уже пройденный путь `g`; быстрее, но не гарантирует оптимум.
3. *Что такое «orthogonal-ray greedy»?*  
   — Метод, который смотрит в ортогональных направлениях лучами и делает жадные выборы по варианту задания — приближённый метод, экономит время за счёт качества.
4. *Какие метрики сравнения?*  
   — Время выполнения, число рассмотренных клеток (expanded), итоговая стоимость пути.
5. *Каверз:* как учитывать разную стоимость клеток (terrain cost)?  
   — В A* и Dijkstra вес перехода = стоимость целевой клетки (или среднее), эвристика должна быть скорректирована (Manhattan*minCost) или допускать неконсистентность.

## Тема 1 — Инфиксная нотация  
**Определение / теория (2–3 предложения):**  
Инфиксная нотация — привычный человеку способ записи арифметических выражений, где оператор располагается между операндами (`a + b`). Она требует правил приоритета и/или скобок, чтобы однозначно задавать порядок вычислений.

**Вопросы и ответы:**
1. *Почему инфикс неоднозначен без правил приоритета?*  
   — Если написать `3 + 4 * 2`, без правил неясно, сначала `+` или `*`. Правила приоритета (`*` выше `+`) фиксируют порядок; иначе нужны скобки.
2. *Как парсер превращает инфикс в компьютерное представление?*  
   — Парсер строит дерево разбора (AST): операторы — внутренние узлы, операнды — листья; дерево отражает приоритеты и ассоциативность.
3. *Можно ли выполнять оптимизации на инфиксном AST?*  
   — Да: константное сворачивание (`2+3` → `5`), перестановки, алгебраические упрощения — всё на дереве.
4. *Почему компиляторы обычно не работают с «сырой» инфикс-строкой?*  
   — Потому что дерево даёт структурированное представление, удобное для трансформаций и оптимизаций.
5. *Когда стоит поддержать пользовательский инфикс и когда — нет?*  
   — Для пользовательских калькуляторов и языков — да; для низкоуровневых VM часто используют постфикс/байткод.

## Тема 2 — Постфиксная нотация  
**Определение / теория:**  
В постфиксной (обратной польской) нотации оператор идёт после операндов. Она устраняет скобки и приоритеты — порядок операций однозначен, что удобно для стековой оценки.

**Вопросы и ответы:**
1. *Как вычислять постфикс?*  
   — Используем стек: число → push; при операторе pop b, pop a, вычисляем `a op b`, push результат.
2. *Почему постфикс удобен для виртуальных машин?*  
   — Инструкция-ориентированная архитектура: набор инструкций push/pop и binary op легко трансформировать в байткод.
3. *Как преобразовать дерево выражения в постфикс?*  
   — Делает постфиксный обход (post-order traversal) дерева: left, right, root.
4. *Что сложнее — постфикс или инфикс для человека?*  
   — Человеку постфикс непривычен; для машины — проще.
5. *Какие ошибки при ручном вводе постфикса часты?*  
   — Неправильный порядок операндов, недостаток операндов перед оператором (stack underflow).

---

## Тема 3 — Польская запись (префикс)  
**Определение / теория:**  
Префиксная запись: оператор идёт перед операндами (`+ a * b c`). Удобна для некоторых рекурсивных вычислений и для записи в Lisp-подобных языках.

**Вопросы и ответы:**
1. *Как вычислять префикс?*  
   — Рекурсивно или через стек, читая слева направо: при операторе рекурсивно вычисляем требуемое число аргументов.
2. *Префикс или постфикс — что лучше?*  
   — Одинаково по выразительности; постфикс удобнее для стековой VM, префикс — для рекурсивных парсеров.
3. *Как преобразовать инфикс в префикс?*  
   — Можно реверсировать строку и применить Shunting Yard с адаптацией ассоциативности, или построить AST и вывести preorder.
4. *Где префикс используется на практике?*  
   — В Lisp, и как промежуточное представление в некоторых компиляторах.
5. *Какие преимущества при работе с функциями переменной арности?*  
   — В префиксе проще указать оператор перед аргументами, но нужен способ обозначения числа аргументов (например, скобки/арность).

---

## Тема 4 — Динамическое программирование (DP)  
**Определение / теория:**  
DP — метод решения задач, где проблема разбивается на перекрывающиеся подзадачи; решения подзадач запоминаются и переиспользуются. Требует **оптимальной подструктуры** и **перекрывающихся подзадач**.

**Вопросы и ответы:**
1. *Чем DP отличается от простой рекурсии?*  
   — Рекурсия без мемоизации пересчитывает одни и те же подзадачи; DP сохраняет результаты (таблицы), исключая повторные вычисления.
2. *Когда применять DP?*  
   — Когда есть оптимальная подструктура (решение задачи строится из оптимальных решений подзадач) и количество подзадач не слишком велико.
3. *Примеры классических задач?*  
   — Рюкзак, разрезание стержня, наибольшая возрастающая подпоследовательность, нахождение числа Фибоначчи (оптимально DP).
4. *Какие два подхода DP существуют?*  
   — Top-down (рекурсия + мемоизация) и bottom-up (итеративное заполнение таблицы).
5. *Как выбирать размер таблицы?*  
   — Таблица должна включать все возможные состояния подзадач; важно оценить размер по параметрам (например, n и W для рюкзака).

---

## Тема 5 — Итеративные алгоритмы  
**Определение / теория:**  
Алгоритмы, реализованные циклически (for, while), без явной рекурсии. Итеративный стиль часто более предсказуем по памяти и безопасен от переполнения стека.

**Вопросы и ответы:**
1. *Когда итеративный стиль предпочтительнее?*  
   — Когда глубина рекурсии велика или важна контроль памяти/производительности.
2. *Всегда ли итерация лучше рекурсии?*  
   — Нет: рекурсия может быть чище и проще для рекурсивных структур (деревья); иногда tail recursion оптимизируется компилятором.
3. *Как перевести рекурсию в итерацию?*  
   — Явно моделировать стек вызовов (используя свой стек) или найти DP-решение.
4. *Какие проблемы у итерации?*  
   — Код может стать запутанным при сложной рекурсивной логике.
5. *Примеры из твоих лб:*  
   — Везде итеративный DP и shunting-yard: управление памятью проще и UI-демонстрация детерминирована. :contentReference[oaicite:34]{index=34}

---

## Тема 6 — Жадные алгоритмы  
**Определение / теория:**  
Алгоритмы, которые на каждом шаге выбирают локально оптимальный вариант, надеясь получить глобальный оптимум. Работают быстро, но не всегда дают оптимум.

**Вопросы и ответы:**
1. *Когда жадность даёт оптимум?*  
   — Когда задано свойство «жадного выбора» — локальный оптимум можно расширить до глобального оптимума (напр., Хаффман, минимальное покрытие активностей).
2. *Как проверить корректность жадного алгоритма?*  
   — Доказательством жадного выбора: показать, что существует оптимальное решение, которое делает тот же локальный выбор.
3. *Пример провала?*  
   — 0/1 рюкзак — жадный по ratio может давать неполный/неоптимальный выбор.
4. *Почему жадные быстрые?*  
   — Часто требуют сортировки + линейного прохода → O(n log n).
5. *Как использовать жадную как эвристику?*  
   — В случаях, где нужен быстрый приближённый ответ, или как стартовая часть более сложного алгоритма.

---

## Тема 7 — Коды Хаффмана  
**Определение / теория:**  
Хаффман — жадный алгоритм построения оптимального префиксного кода при известных частотах символов; строит бинарное дерево, объединяя два минимальных узла на каждом шаге.

**Вопросы и ответы:**
1. *Почему код префиксный?*  
   — Потому что никакой код не является префиксом другого; это гарантирует однозначность декодирования.
2. *Где хранится кодовая таблица в бинарном файле?*  
   — В заголовке: пара (символ, длина, биты) либо сериализованное дерево.
3. *Можно ли декодировать поток без таблицы?*  
   — Нет: нужен способ восстановить дерево; можно хранить дерево в заголовке компактно.
4. *Что если частоты меняются со временем?*  
   — Используют адаптивные/динамические версии (adaptive Huffman) или арефметическое кодирование.
5. *Почему Хаффман оптимален?*  
   — Доказуема жадным обменным аргументом: объединение двух наименьших по частоте символов не ухудшает оптимальность.

## Тема 8 — Поиск в ширину (BFS)  
**Определение / теория:**  
BFS — обход графа по уровням: сначала все вершины на расстоянии 0, затем 1, и т. д. Реализуется через очередь; находит кратчайший путь в невзвешенных графах.

**Вопросы и ответы:**
1. *Почему BFS даёт кратчайший путь в невзвешенном графе?*  
   — Потому что первый раз, когда мы достигаем целевой вершины, мы делаем это по минимальному числу шагов (уровней).
2. *Какая сложность?*  
   — O(V + E).
3. *Как хранить путь?*  
   — Через массив `prev[]`, по которому восстанавливают путь обратно.
4. *Где BFS бесполезен?*  
   — Во взвешенных графах с разными весами — там нужен Dijkstra или Bellman–Ford.
5. *Как использовать BFS для потоков/компонент?*  
   — Компоненты связности для неориентированных графов можно получить вызовом BFS со всех непосещённых вершин.

---

## Тема 9 — Поиск в глубину (DFS)  
**Определение / теория:**  
DFS посещает как можно глубже по одной ветви, затем откатывается; реализуется рекурсивно или через стек. Используется для проверки циклов, топологической сортировки, компонент.

**Вопросы и ответы:**
1. *Как найти цикл в графе с помощью DFS?*  
   — Для ориентированного графа: метки состояний (unvisited, visiting, visited); если наткнулись на `visiting` — цикл найден.
2. *Как получить топологическую сортировку?*  
   — Заполнять список вершинами в порядке завершения (post-order), затем реверсировать.
3. *Когда DFS полезен?*  
   — При задачах, где важно проникнуть в глубину (поиск пути, компоненты).
4. *Сложность DFS?*  
   — O(V + E).
5. *Каверз:* стековая реализация vs рекурсивная — различия?  
   — Рекурсивная проще, но риск переполнения стека; стек даёт контроль и возможность сохранения состояния.

---

## Тема 10 — Остовное дерево / Минимальное остовное дерево (Прим)
**Определение / теория:**  
Остовное дерево соединяет все вершины без циклов; минимальное остовное дерево (MST) — одно с минимальной суммой весов. Прим — алгоритм, растущий от начальной вершины, добавляет минимальное внешнее ребро.

**Вопросы и ответы:**
1. *Почему MST важно?*  
   — Находит минимальную стоимость соединения сети (развертывание сетей, кластеризация).
2. *Сложность Прима?*  
   — O(E log V) при использовании min-heap.
3. *Как начать Прим?*  
   — Выбрать стартовую вершину, пометить её, добавлять минимальные ребра на границе.
4. *Как хранить граф?*  
   — Для Прима удобно хранить списки смежности и использовать приоритетную очередь.
5. *Каверз:* что если граф не связен?  
   — Тогда получится лес MST — несколько деревьев; полный MST не существует.

---

## Тема 11 — Остовное дерево / Краскал
**Определение / теория:**  
Краскал строит MST сортировкой всех рёбер по возрастанию веса и добавляет их, если они не образуют цикл (проверка через DSU — disjoint set union).

**Вопросы и ответы:**
1. *Почему нужен DSU?*  
   — Чтобы быстро проверять, принадлежат ли концы ребра одной компоненте (find) и объединять компоненты (union) — операции почти O(α(n)).
2. *Сложность Краскала?*  
   — O(E log E) из-за сортировки рёбер, плюс DSU почти O(1) на операцию.
3. *Когда Краскал лучше Прима?*  
   — На разреженных графах, где E << V².
4. *Как хранить результат?*  
   — Список рёбер MST.
5. *Каверз:* как обработать параллельные ребра?  
   — Сортировка учитывает вес; параллельные ребра с разными весами рассматриваются как отдельные, добавляется только самое лёгкое, если не ведёт к циклу.

---

## Тема 12 — Флойд–Уоршелл
**Определение / теория:**  
Алгоритм нахождения кратчайших путей между всеми парами вершин в графе (матрица расстояний). Использует тройной цикл и промежуточные вершины.

**Вопросы и ответы:**
1. *Почему кубическая сложность?*  
   — Потому что есть три вложенных цикла по числу вершин (k,i,j).
2. *Можно ли улучшить?*  
   — На общих графах нет простого ускорения; для разреженных графов используют многократные Dijkstra.
3. *Как обнаруживать отрицательные циклы?*  
   — После алгоритма, если diag d[i][i] < 0 — есть отрицательный цикл.
4. *Где полезен?*  
   — В задачах с небольшим V, где нужны все пары расстояний (транспорт, маршрутизация).
5. *Как восстанавливать пути?*  
   — Хранить `next[i][j]` и реконструировать путь последовательными переходами.

---

## Тема 13 — Форда–Фалкерсона (максимальный поток)
**Определение / теория:**  
Алгоритм для поиска максимального потока в сети, ищет увеличивающие пути в остаточном графе, увеличивает поток до тех пор, пока есть путь от source до sink.

**Вопросы и ответы:**
1. *От чего зависит скорость?*  
   — От выбора увеличивающих путей; наивная реализация может работать плохо (зависит от величин потоков).
2. *Как улучшить?*  
   — Edmonds–Karp использует BFS для поиска кратчайших по рёбрам путей → O(V E²). Dinic использует уровневую сеть и даёт O(E sqrt(V)) для единичных весов.
3. *Как представляется остаточный граф?*  
   — Для ребра u→v с пропускной способностью c и текущим потоком f, в остаточном графе есть ребра u→v (c−f) и v→u (f).
4. *Почему отрицательные веса неуместны?*  
   — Форда–Фалкерсона оперирует пропускными способностями (non-negative).
5. *Применение:* сети, потоки, паросочетания.

---

## Тема 14 — Дейкстра
**Определение / теория:**  
Алгоритм нахождения кратчайших путей от одной вершины в графе с неотрицательными весами. Использует приоритетную очередь и релаксацию рёбер.

**Вопросы и ответы:**
1. *Почему не работает при отрицательных рёбрах?*  
   — Алгоритм полагается, что когда вершина извлечена из очереди, её дистанция финальная; с отрицательными рёбрами это неверно.
2. *Сложность при использовании min-heap?*  
   — O((V + E) log V) ≈ O(E log V).
3. *Как восстановить путь?*  
   — Массив `prev[]`, аналогично.
4. *Как ускорить?*  
   — В практических реализациях используют биномиальную/фибоначчиеву кучу; для специальных графов есть оптимизации.
5. *Сравнение с Bellman–Ford:* Дейкстра быстрее, но ограничен неотрицательными весами.

---

## Тема 15 — Беллман–Форд
**Определение / теория:**  
Алгоритм для кратчайших путей от одной вершины, работает при наличии отрицательных ребер и может обнаруживать отрицательные циклы.

**Вопросы и ответы:**
1. *Как он работает?*  
   — Проводит |V|-1 итераций релаксации всех рёбер; если на |V|-й итерации дистанции улучшаются — есть отрицательный цикл.
2. *Сложность:*  
   — O(VE).
3. *Когда использовать?*  
   — Когда есть отрицательные веса или нужно обнаружить отрицательные циклы.
4. *Можно ли ускорить?*  
   — Есть варианты с очередью (SPFA), но в худшем случае SPFA медленнее.
5. *Как обрабатывать отрицательный цикл в контексте задачи?*  
   — Если цикл достижим из источника и может уменьшать стоимость до −∞, многие задачи не имеют корректного смысла; нужно корректировать модель.

---

## Тема 16 — Волновой алгоритм (Ли)
**Определение / теория:**  
Алгоритм поиска кратчайшего пути на решётке (grid) по равновесным шагам, аналог BFS, особенно применим для роботики и PCB трассировки.

**Вопросы и ответы:**
1. *Почему гарантирует кратчайший путь?*  
   — Потому что расширяется слоями, каждый шаг увеличивает расстояние на единицу.
2. *Как реализуется?*  
   — Очередь точек; пометка расстояний; восстановление путем обратного следования.
3. *Поддержка препятствий/стоимостей?*  
   — Для препятствий — просто непреодолимые клетки; для весов нужен модифицированный алгоритм (Dijkstra/A*).
4. *Сложность:* O(nodes) — линейная по числу клеток.
5. *Каверз:* как делать для диагоональных переходов?  
   — Нужно скорректировать расчёт расстояний и эвристику (если применимо).

---

## Тема 17 — Лучевой поиск (Ray / beam search)  
**Определение / теория:**  
Лучевой (beam) поиск — эвристический жадный метод, который на каждом уровне держит только `k` лучших кандидатов (beam width), сокращая расход памяти и времени.

**Вопросы и ответы:**
1. *Почему полезен?*  
   — Ограничивает экспоненциальный рост ветвления, применим в NLP, поиске планов.
2. *Недостатки?*  
   — Может отбросить глобально оптимальный путь, т.к. оставляет только локально лучшие `k`.
3. *Как выбрать ширину beam?*  
   — Баланс между качеством решения и ресурсами; обычно опытно.
4. *Как сравнивать с A*?*  
   — Beam корректен как эвристика — быстрее, но не оптимален; A* при допустимой эвристике оптимален.
5. *Применение в лаб.7:* Orthogonal-ray greedy — похожая идея, ограничивает ширину обзора.

---

## Тема 18 — A*  
**Определение / теория:**  
A* — эвристический алгоритм поиска путей, использует функцию `f(n)=g(n)+h(n)` (g — стоимость пути от start, h — эвристическая оценка до goal). При допустимой и согласованной эвристике A* гарантирует оптимальность и эффективность.

**Вопросы и ответы:**
1. *Что значит допустимая эвристика?*  
   — `h(n)` не превосходит реальную минимальную стоимость от `n` до цели; тогда A* не пропустит оптимальный путь.
2. *Почему согласованность (consistency) важна?*  
   — Согласованность гарантирует, что `f`-значения не убывают по пути; это упрощает реализацию и гарантирует, что после извлечения вершины из очереди её расстояние финально.
3. *Как выбрать `h` для сетки?*  
   — Manhattan для 4-направленной сетки, Euclidean для диагональных переходов; умножение на минимальную стоимость клетки, если веса >1.
4. *Когда A* деградирует до Dijkstra?*  
   — Когда `h = 0`.
5. *Как измерять эффективность?*  
   — По количеству открытых/рассмотренных вершин и по времени; хорошая эвристика значительно сокращает пространство поиска.
